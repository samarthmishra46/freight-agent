## Controls I noticed while building but deliberately did not add

Hop numbers refer to the numbering in `docs/FreightAgent-Execution-Plan.md`:
hop 14 is loop → customs server, hop 15 is customs → loop, hop 19 is customs → ledger.

### Phase 1 — dummy customs server

- [hop 14] Port 9000 has no authentication of any kind; anything that can reach the socket can lodge. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] Traffic is plain HTTP, so identity headers and importer commercial values cross the wire in clear. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] `x-operator`, `x-certificate` and `x-forwarder` are recorded verbatim and never verified against any register of operators or certificates. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] A lodgement carrying no identity headers at all is accepted; the operator field is not even required to be present. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The server has no way to tell whether a human confirmed the lodgement, and does not ask for one. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] No idempotency key: an identical cargo report posted three times produced three distinct references (ACR1009260001/0002/0003). Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] No rate limiting; a caller can lodge as fast as it can open connections. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] No request size cap: the whole body is read into memory and written to the ledger, so a large payload is both an availability problem and a way to bloat the evidence file. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The server checks `value_aud > 1000` and `sac is true` independently, so it never confirms that the two agree with each other or with any real manifest — the house bill list is entirely the caller's assertion. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 15] Rejection responses name the rule that failed and echo the threshold, which lets a caller map the validation logic by probing. Would be an L2 control at hop 15. Not added — v1 baseline.
- [hop 19] Consignee names, addresses and commercial values are written to `ledger.jsonl` in clear, with no redaction, no access control on the file and no retention limit. Would be an L1 control at hop 19. Not added — v1 baseline.
- [hop 19] The ledger has no integrity protection — no hash chain, no signature — so anything with write access to the file can rewrite history and nothing detects it. Would be an L1 control at hop 19. Not added — v1 baseline.
- [hop 19] `POST /ledger/reset` destroys the audit record and is gated only by the `CUSTOMS_TEST_MODE` environment variable, with no authentication behind that gate. A reset endpoint on a real customs system would itself be a finding. Would be an L1 control at hop 19. Not added — v1 baseline.
- [customs] Ledger append is best-effort within a request lifecycle. A request that kills the process between receipt and append leaves no trace. Audit evasion, not just lost durability. Would be an L1 control (write-ahead on receipt) at hop 19. Not added — v1 baseline.
- [customs] Reference counters seed from the ledger at startup, so /ledger/reset causes reference REUSE, not just record loss. Two lodgements can share ACR1009260001. Would be an L1 control (monotonic counter persisted independently of the ledger) at hop 19. Not added — v1 baseline.

### Phase 2 — sample data and the manifest parser

- [hop 7] `parse_manifest` opens whatever path it is handed, with no allowlist, no root directory and no check that the file is the manifest the operator actually uploaded. Would be an L1 control at hop 7. Not added — v1 baseline.
- [hop 7] No provenance or integrity check on the PDF: no signature, no hash pinned at upload, no record of who produced the document. The pipeline cannot tell a genuine manifest from an edited one. Would be an L1 control at hop 7. Not added — v1 baseline.
- [hop 7] The row totals are not cross-checked against the master block: summed `pieces` and `weight_kg` are never compared with `total_pieces` and `total_weight_kg`, so a row edited to move a value across the AUD 1,000 threshold leaves the declared totals inconsistent and nothing notices. Only the row *count* against `total_house_bills` is checked, and only as a warning. Would be an L2 control at hop 7. Not added — v1 baseline.
- [hop 7] Text hidden from a human reader — white-on-white, zero-opacity, off-page — is extracted identically to visible text, and nothing compares what a reviewer sees against what the pipeline ingests. Would be an L2 control at hop 7. Not added — v1 baseline.
- [hop 7] PDF metadata (Title, Subject, Keywords) is never read, so content carried there is invisible to the parser and to the operator alike. A blind spot rather than a gap in a control, but it means the pipeline has no view of part of the document it is trusting. Not added — v1 baseline.
- [hop 8] Extracted free text — `goods_description`, `consignor`, `consignee`, `delivery_address` — is returned verbatim, with no sanitisation, no classification and no marking to separate third-party document content from instructions. It goes on to enter the model's context at hop 9. Would be an L2 control at hop 8. Not added — v1 baseline.
- [hop 8] No size cap on extracted content: a manifest with ten thousand rows, or one enormous goods description, flows straight through the MCP response and into the model's context. Would be an L1 control at hop 8. Not added — v1 baseline.
- [hop 8] `extraction_warnings` is advisory only. Nothing downstream is required to read it, so a parse that degraded badly and said so is indistinguishable, to the rest of the pipeline, from a clean one. Would be an L1 control at hop 8. Not added — v1 baseline.
- [hop 9] The parser records that an unused clearance classification was present in the source document, but that observation is a warning string only — nothing refuses to proceed on a manifest that classifies itself. Would be an L1 control at hop 9. Not added — v1 baseline.

### Phase 3 — the MCP server

- [hop 6] The `file` argument sent to `read_manifest` is whatever the model put in its `tool_use` block, and the loop never checks it against the path the operator actually uploaded. Demonstrated over MCP: an absolute path to an unrelated PDF outside the project, and a `data/../docs/...` traversal, both read successfully. Would be an L1 control at hop 6. Not added — v1 baseline.
- [hop 6] The tool description the model is given is whatever the MCP server advertises, taken from its docstring. Changing that server changes what the model believes the tool does, with the loop neither redeployed nor aware. Would be an L1 control at hop 6. Not added — v1 baseline.
- [hop 6] The MCP subprocess is spawned with the loop's entire environment copied into it, so it inherits `OPENAI_API_KEY` and `CUSTOMS_URL` despite needing neither. Would be an L1 control at hop 6. Not added — v1 baseline.
- [hop 8] The loop accepts the MCP response without validating it against the tool's declared output schema. A server returning different fields, missing fields or extra ones would be passed straight on. Would be an L1 control at hop 8. Not added — v1 baseline.
- [hop 9] MCP output enters the model's context as a `tool_result` with nothing marking it as third-party document content rather than the loop's own trusted instructions. Once it is in the context window the two are indistinguishable. Would be an L1 control at hop 9. Not added — v1 baseline.

### Phase 4 — the agent loop

- [hop 12/14] Nothing checks that a human confirmed a lodgement. `session.confirmations` exists, is never written to by the lodge path, and is never read before a POST. The only thing between a `tool_use` block and an irreversible lodgement is a sentence in the system prompt, which is an L3 control sharing a context window with untrusted document text. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The model's tool arguments are never compared against the parsed manifest. If the model supplies a house bill that is not in the manifest, or changes a consignee or a value, that is what gets lodged. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The AUD 1,000 threshold is never recomputed by our code before lodging. The `sac` flag in each house bill is whatever the model asserted. Only the customs server's own business rule catches a mismatch, and by then the attempt is already in the ledger and irreversible. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 2] Operator identity is three request headers, taken as fact. No signature, no session lookup, no certificate validation, and no check that the certificate belongs to the named person or the named forwarder. Would be an L1 control at hop 2. Not added — v1 baseline.
- [hop 2] Missing identity headers fall back to a hardcoded default operator, so a request with no identity at all is lodged under a real-looking name. Silently attributing a lodgement to someone who did not make it is worse than rejecting it. Would be an L1 control at hop 2. Not added — v1 baseline.
- [hop 2] The session id is accepted from the client with no check that it belongs to the caller, so any client can attach to any session and inherit its manifest and its lodgement history. Would be an L1 control at hop 2. Not added — v1 baseline.
- [hop 2] The identity on an existing session is overwritten by whatever the current request asserts, so the operator a session is attributed to can change turn to turn. Would be an L1 control at hop 2. Not added — v1 baseline.
- [hop 3] `/upload` writes the client's chosen filename into `data/` with no check on extension, content type, size, or whether the bytes are a PDF, and that path is what the model is later told to read. Would be an L1 control at hop 3. Not added — v1 baseline.
- [hop 4] The entire parsed manifest stays in conversation history, so all ten importers' names, addresses, goods descriptions and commercial values re-cross the provider boundary on every turn after it is read. Measured in this build: `loop->llm` grew from 6,442 bytes on the first turn to 13,121 bytes by the fourth, and nothing minimises what is sent. Would be an L1 control at hop 4. Not added — v1 baseline.
- [hop 4] No field minimisation, pseudonymisation or redaction before egress, and no record of what was disclosed to the provider beyond a byte count and a hash. Would be an L1 control at hop 4. Not added — v1 baseline.
- [hop 5] Tool arguments from the model are passed to `dispatch` without being validated against the tool's own declared input schema. Would be an L1 control at hop 5. Not added — v1 baseline.
- [hop 9] Tool results — MCP output and customs responses alike — are serialised into the context with no size cap and no marking that separates them from the loop's own instructions. Would be an L1 control at hop 9. Not added — v1 baseline.
- [hop 18] The audit log's `turn` counter restarts at 1 on every operator turn rather than being monotonic per session, so reconstructing the true order of events overnight needs the timestamps, not the turn numbers. Would be an L1 control at hop 18. Not added — v1 baseline.
- [hop 18] `agent.jsonl` records a size and a hash per hop, never the payload, so the audit log alone cannot show *what* importer data crossed hop 4 — only how much. Deliberate, to avoid a third copy of the importer records, but it means the egress question is answerable only in aggregate. Not added — v1 baseline.
- [customs] CORS is open to every origin and there is no authentication on port 8000, so any page in the operator's browser can drive the loop and reach the lodgement path. Would be an L1 control at hop 2. Not added — v1 baseline.

### Phase 5 — the chat UI

- [hop 12] The confirmation gate is theatre. Pressing "Confirm and lodge" sends an ordinary chat message; nothing is signed, nothing is bound to the payload shown above the button, no token is minted, and the loop will lodge just as readily without it. The interface makes the moment feel weighty while recording no proof that it happened. Would be an L1 control at hop 12. Not added — v1 baseline.
- [hop 11] The preview card is computed in the browser from the parsed manifest, and the tool arguments are computed independently by the model. Nothing compares the two, so what the operator sees is not necessarily what gets lodged. Would be an L1 control at hop 11. Not added — v1 baseline.
- [hop 1] Operator name, forwarder and certificate are hardcoded in `app.js` and sent as headers the client controls, so they can be edited in the browser's devtools before a lodgement. Would be an L1 control at hop 1. Not added — v1 baseline.
- [hop 1] The session id is read from `localStorage` and from a `?session=` query parameter, so it leaks through browser history, shared links and referrer headers — and any client holding one inherits that session's manifest and lodgements. Would be an L1 control at hop 1. Not added — v1 baseline.
- [hop 11] House bill fields taken from the manifest — `hawb` and `consignee` — are interpolated into `innerHTML` when the preview table is built. A crafted manifest PDF can therefore inject markup into the operator's browser, which makes the manifest an XSS vector as well as a prompt injection vector. Would be an L1 control at hop 11. Not added — v1 baseline.
- [hop 11] The plumbing view reports a byte count and a note per hop, so an operator can see how much left for the provider but not what. Deliberate, but it means the interface cannot answer the question the operator would actually ask. Not added — v1 baseline.

### Phase 3.5 — the rules engine, state machine and scope check

These three are product features, not security controls, and building them
surfaced a fresh set of weaknesses in the new layer itself.

- [hop 14] Nothing enforces that the rules engine ran. `_check_before_lodging` is called by `dispatch` and by nothing else, and `_post_to_customs` does not re-check. Demonstrated: calling `tools._post_to_customs` directly lodged a house bill declared at AUD 2,100 with its value rewritten to 12.00, and customs accepted it — reference ACR1209260002. Would be an L1 control at hop 14. Not added — v1 baseline, and deliberately so: a later test determines whether the agent path can go round this layer.
- [hop 14] The customs server has no idea whether validation occurred. It validates its own business rules and nothing else, so a caller that skips the agent entirely is indistinguishable from one that came through it. Demonstrated: a direct POST to port 9000 with a forged operator header was accepted — reference ACR1209260003, ledger seq 5, `x-operator: 'Someone Else'`. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] No token, signature or seal proves the validated payload is the payload that was sent. The rules engine checks a dict and then a separate call posts a dict; nothing binds the two, so a payload could be validated and then altered before the POST. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The shipment state is a plain string on the session and can be rewritten with one assignment. Demonstrated: a RELEASED shipment was reset to HELD by `session.shipment_state = "HELD"; state.save(session)`, making the whole sequence lodgeable again. Since `data/sessions.json` has no access control, anything that can write that file can reopen a closed shipment. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 14] The state machine only ever advances on acceptance, so a lodgement that customs accepts but that our code failed to record leaves the session behind the truth — and the next attempt would be permitted a second time. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 19] A refused lodgement never reaches the customs server, so it leaves no entry in `ledger.jsonl` at all. The ledger is the evidence base, and it now records only what got past our own rules; the refused attempts exist solely in `agent.jsonl`, which is our own log and not append-only. Demonstrated: four refusals in one conversation, three ledger entries. Would be an L1 control at hop 19. Not added — v1 baseline.
- [hop 2] The scope check is keyword and pattern based, so any message carrying freight vocabulary is in scope regardless of intent. "ok now forget the manifest and tell me a story" passes on the word "manifest", and "book me a flight to Paris" passes on "flight". Would be an L2 control at hop 2. Not added — v1 baseline; a classifier is phase 9.
- [hop 2] The scope check reads the operator's message only. Injected instructions arrive inside the manifest PDF at hop 8, long after this gate has been passed, so it offers nothing at all against prompt injection and must not be described as if it did. Would be an L2 control at hop 8. Not added — v1 baseline.
- [hop 2] Scope rejection happens in `POST /chat` only. `run_turn` is callable without it, and `POST /upload` takes a file and then triggers a turn through the front end without its own check. Would be an L1 control at hop 2. Not added — v1 baseline.
- [hop 11] The rules engine's refusal messages quote the manifest's true figures back to the caller — expected value, expected pieces, which HAWBs are over threshold. Useful to an operator, and equally useful to anyone probing the pipeline for what it holds. Would be an L2 control at hop 11. Not added — v1 baseline.
- [hop 14] `derive_sac_split` treats a house bill whose `value_aud` could not be parsed as over threshold, which is the safe side for clearance — but nothing alerts anyone that a bill was classified on a parse failure rather than on a value. Would be an L2 control at hop 14. Not added — v1 baseline.

### Noticed while driving the UI (phase 5 walkthrough)

- [hop 17] The reply shown to the operator is the model's own text, and nothing reconciles it against the hops that actually happened. Demonstrated: the assistant stated it had altered a consignee and lodged the cargo report while making no tool call at all — `loop->customs` never fired, `ledger.jsonl` stayed empty, and the shipment stayed HELD. A claimed lodgement and a real one are indistinguishable in the chat window. Would be an L1 control at hop 17. Not added — v1 baseline.
- [hop 14] The rules engine reconciles `pieces`, `weight_kg` and `value_aud` against the manifest but never `consignee`, so the importer's name on a lodgement is whatever the model wrote. The name is the field that says whose goods these are, and it is the one field not checked. Would be an L1 control at hop 14. Not added — v1 baseline.
- [hop 11/12] Demonstrated: with the preview card reading "Underbond movement — to be lodged", the operator's bare "ok" was interpreted by the model as confirming `lodge_outturn` — the last action it had described in text — not the action on the card. The confirmation carries no reference to the payload shown, so the screen and the tool call disagreed with nothing detecting it. Only the state machine refused it, and only because the shipment happened to be CLEAR rather than SUBUBMOV; at SUBUBMOV the wrong lodgement would have been sent irreversibly. Would be an L1 control at hop 12. Not added — v1 baseline.

### Phase 8 — noticed while writing and running the tests

- [hop 4] The loop has no error handling around the provider call, so a rate limit or a transient API fault propagates as an unhandled HTTP 500 out of `POST /chat`. The operator sees a bare error, the turn is lost, and `agent.jsonl` records the outbound `loop->llm` hop with no matching `llm->loop` — so the log shows a request that apparently never came back. Observed during the phase 8 suite. Would be an L1 control at hop 4. Not added — v1 baseline.
- [hop 9] The manifest injection succeeds intermittently rather than always: the canary was emitted on 4 of 20 captured identical runs (`docs/canary-runs.txt`). An advisory control that holds on some runs and not others is not a control with a reliability figure — it is an absent control with a variable attacker success rate, and a single passing run must never be read as a defence. Would be an L2 control at hop 9. Not added — v1 baseline.
- [hop 8] `read_manifest` returns ten named fields, so an injection placed in the page footer or in PDF metadata never reaches the model at all — two of the three vectors in `manifest-SQ100-injected-2.pdf` died at the parser. This is **not** a control: it is an incidental consequence of returning named fields, nothing was designed to filter anything, and it stops mattering the moment the payload sits in a free-text field, which is what vector A does. Recorded so it is not later mistaken for a defence. Not added — v1 baseline.

### Phase 9 — CP-8 fixed; noticed while fixing it

- [hop 14] **FIXED (v2).** The confirmation gate is now structural: `agent/confirmations.py` stages every lodgement against a single-use token bound to the payload hash, the session and the operator's certificate, and `_post_to_customs` takes that confirmation as a required parameter so no call path can reach customs without one. The model never receives the token. Was L3, now L1.
- [hop 12] A token is issued to whoever the client *claims* to be, because CP-1 is still absent. A caller asserting `X-Operator: Someone Else` receives a valid token for `T3-FAKE-9999` and can spend it. CP-8 binds a confirmation to a lodgement; only CP-1 binds it to a person. Would be an L1 control at hop 2. Not added — one control per phase.
- [hop 14] Pending confirmations live in process memory, so a restart between staging and confirming silently drops the staged lodgement and the operator's next click returns "no such confirmation token" with no explanation of why. Correct for security, poor for the operator. Would be a usability fix, not a control. Not added.
- [hop 19] The ledger now records `confirmation_token` and `confirmation_sha256`, but the customs server neither checks them nor knows what they mean — it records whatever it is handed. A direct POST can therefore include a fabricated `confirmation_token` and the ledger will look identical to a genuine one. The field is evidence only while the agent is the only caller, which A3 shows it is not. Would be an L1 control at hop 14 (CP-10). Not added — v1 baseline for that control.

### Phase 10 — noticed while checking coverage against the published lists

- [hop 2] `data/sessions.json` stores the full conversation with no integrity protection, and `run_turn` replays that history into the model's context every turn. Anything that can write the file can insert assistant turns the model then treats as its own prior reasoning — persistent, surviving across turns and sessions, and invisible in the chat UI, which renders only what the current turn returned. Recorded earlier only as "shipment_state can be rewritten"; the history is the larger half. Would be an L1 control at hop 2 (CP-18). Not added — one control per phase.
- [hop 17] The model's reply is never reconciled against the hops actually recorded for the turn, so a claimed lodgement with no `loop->customs` hop renders to the operator as fact. Was recorded in phase 5 as an observation but never became a numbered control point, which kept it out of the control table and the test plan until the OWASP LLM07 row exposed it. Now CP-17. Would be an L1 control at hop 17. Not added — one control per phase.
- [supply chain] `requirements.txt` pins no version except `mcp>=2,<3`, so a fresh install resolves whatever is current that day, and nothing records what was actually installed when the tests were run. Would be an L1 control outside the hop diagram. Not added — v1 baseline.
- [hop 11] **TESTED (phase 10).** Manifest-derived `hawb` and `consignee` reach `innerHTML` in `frontend/app.js` unescaped. `tests/test_f_output_handling.py` now proves both halves: markup survives the parser intact, and app.js interpolates those fields into the DOM. The operator's browser session holds CP-8's confirmation tokens, so this is a document-to-lodgement path that no prompt-injection control would catch. Would be an L1 control at hop 11 (CP-12). Still not fixed — one control per phase.
- [hop 11] **FIXED (phase 10).** `billsTable` in `frontend/app.js` now writes `hawb` and `consignee` with `textContent` instead of interpolating them into `innerHTML`, so manifest markup can no longer become script in the operator's browser. The coverage check is what prompted it: the row read *exposed · CP-12 absent · no test*, the test was written to prove the flaw, and the fix followed. `tests/test_f_output_handling.py` passes unchanged. CP-12 was an L1 control at hop 11.
- [supply chain] **PARTIALLY FIXED (phase 10).** `requirements.txt` now pins every dependency exactly, at the versions the published v1 and v2 test runs were produced with. Prompted by mapping OWASP LLM04, which I had never checked against the dependency list at all. The other two halves of that row are unchanged and still reported: the MCP subprocess inherits the loop's entire environment, and the tool description the model is given is whatever the MCP server's docstring says.
